# Wetchah — audit des accès et plan d’amélioration

**5 novembre 2026 · Périmètre : `wetchah_app` et `wetchah_erp`.** Source métier : organisation fournie par le commanditaire. Code examiné : APP `1b43be8`, ERP `dcbde94`, dépôts propres avant audit. Les modifications de cette mission sont documentaires ; aucune correction applicative ni action de production n’a été effectuée.

**Conclusion : le socle existe, mais les droits actuels ne respectent pas le circuit achats–contrôle–RAF demandé.** Les priorités sont la révocation des accès ERP, la connexion ERP, la protection des commandes publiques, puis la matrice métier et le cycle d’inventaire. Aucun incident réel ni compromission de production n’est établi.

## 1. Constats prioritaires

Élevée = accès sensible ou intégrité métier compromis ; modérée = exposition limitée ou protection de compte insuffisante. « Reproduit » signifie test HTTP ou résolveur local avec données fictives ; « code » signifie chemin établi mais non exploité. Les configurations et exceptions effectivement déployées ne sont pas connues. Aucun constat n’est classé critique sans preuve suffisante de son impact réel.

Dans les références, **APP** désigne `wetchah_app`, **ERP** désigne `wetchah_erp`. Les chemins et lignes sont relatifs au dépôt indiqué, dans les commits ci-dessus.

La hiérarchie d’encadrement n’implique pas automatiquement l’héritage des écritures. Le périmètre est l’établissement, puis le service, dépôt ou restaurant affecté.

**Fusion du doublon contrôle.** Conserver `controller` comme identifiant cible, renommer son libellé si nécessaire et retirer `quality_auditor` de l’attribution. Avant migration : exporter affectations, niveaux, refus, exceptions, périmètres et références de journal ; simuler les droits effectifs avant/après. Conserver les anciens libellés dans l’historique ; prévoir migration idempotente et retour arrière. Mettre à jour `DutySegregation`, le catalogue, les écrans ERP/APP, notifications et tests.

**À préciser avant le lot inventaire :** « deux jours suivant l’inventaire » = 48 heures à partir de quel instant, ou deux jours calendaires ? Le compteur ne doit pas repartir à la validation RAF. ## 3. Architecture et état des lieux

Deux applications Laravel/Blade avec Alpine, Tailwind et Vite. Versions verrouillées : Laravel **12.62.0 APP**, **12.54.1 ERP**. L’ERP est une console de supervision/propriétaires ; les opérations hôtelières vivent principalement dans l’APP. Le modèle prévu est une instance et une base PostgreSQL par établissement, provisionnées par l’ERP. L’isolation réelle des déploiements n’a pas été vérifiée : l’absence de filtre `tenant_id` dans l’APP ne suffit donc pas à conclure à une fuite entre hôtels.

L’APP dispose d’un catalogue de rôles/droits, d’un résolveur central, de couches d’exceptions ERP/hôtel et de contrôles de séparation des tâches. L’ERP pilote ces droits par API. Cette base est réutilisable ; aucune réécriture ni nouvelle stack n’est justifiée par l’audit.

**F** = parcours ciblés réussis localement ; **P** = partiel/non conforme ou validation incomplète ; **M** = capacité demandée non trouvée dans les composants examinés. F n’atteste ni la production ni tout le module.

## 5. Contrôles réellement effectués et limites

Tests sur copies temporaires sans `.env` réel ni données métier, avec **PHP 8.4.27**, image locale `pms-app`, réseau coupé, utilisateur non privilégié et SQLite en mémoire. Dépendances du dépôt montées en lecture seule ; cache de test séparé. Un `.env` fictif a corrigé les avertissements de préparation du premier passage.

|---|---|

Parmi les réussites, trois tests ajoutés pour l’audit confirment des comportements indésirables, pas des protections. |

Les familles de contrôle suivent [OWASP ASVS 5.0.0](https://asvs.owasp.org/), les méthodes [WSTG 4.2](https://owasp.org/www-project-web-security-testing-guide/) et le risque d’accès par identifiant [API1:2023](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/). Il ne s’agit pas d’une certification de conformité.
